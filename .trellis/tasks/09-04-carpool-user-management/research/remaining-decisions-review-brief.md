# 剩余决策独立审查任务

## 目的

独立审查“拼车用户管理第一阶段”的剩余产品与技术决策，挑战当前方案中的隐含假设，并给出能够直接写入 PRD、设计和实施计划的明确建议。

## 已经由用户确定、不得擅自推翻的边界

- 第一阶段由管理员手动分配，不做用户自助上车、下车或换车。
- 采用 CPA 进程内模块化二开和独立 Web 前端。
- 保留 `/management.html`，新增 `/carpool/`，第一阶段不 fork 现有管理前端。
- 使用 SQLite，限定单机、单 CPA 实例。
- 网页使用用户名、密码和服务端会话；代理客户端使用独立用户 API Key。
- 每名乘客最多一个当前车辆。
- 每个上游账号最多分配给一辆当前车辆，不跨车共享。
- 所有规划文档使用简体中文，代码注释仍使用英文。

## 需要审查并形成推荐的事项

1. 乘客与管理员应看到哪些用量指标、统计周期和无上游用量数据时的语义。
2. 同车成员身份展示和他人用量粒度，如何兼顾拼车透明度与隐私。
3. 上游账号状态的安全 DTO、状态来源、刷新频率和“未知”语义。
4. 第一阶段是否只展示用量，还是执行用户、车辆或账号额度限制。
5. 现有全局 `api-keys` 的兼容策略，以及文件、Git、对象存储、PostgreSQL 和 Home 模式的边界。
6. 初始管理员创建、密码重置、会话撤销、API Key 数量与轮换等身份生命周期。
7. 数据保留、审计、删除语义、备份恢复和 SQLite 并发策略。
8. 是否还有会改变第一阶段验收行为但尚未显式决定的事项。

## 审查要求

- 先检查仓库代码、测试、配置和现有任务文档；能够由仓库回答的事实不得反问用户。
- 区分“第一阶段必须决定”“可以采用安全默认值”“明确推迟到后续阶段”。
- 每项给出一个明确推荐、理由、主要代价、失败模式和至少一条可验证的验收条件。
- 给出具体文件路径或代码锚点作为证据。
- 不修改业务代码、不启动实现、不提交 Git。
- 发现原方案存在安全或一致性缺陷时直接指出，不因已有推荐而迎合。
