# 乘客端密码重置、用量配额与管理记录增强

## 目标

让乘客在密码被管理员重置后能清楚地完成后续操作，并让管理员和乘客能围绕
乘客限额、实际用量和使用记录获得可理解、可核对的界面。
管理端与乘客端通过 `qiaomu-design` 全面重设计，放弃原有前端样式、导航构成与布局骨架。

## 背景与已确认事实

- 现有管理员重置密码会生成一次性临时密码、增加 `password_version`，并把
  `must_change_password` 设为 `true`。这会使旧网页会话失效，但不会删除乘客的
  车辆、成员关系、API Key 或历史用量。
- 乘客用临时密码登录后，现有前端只显示“修改密码”导航；现有后端也会在
  完成改密前拒绝车辆、成员用量、账号状态和 API Key 接口。
- 现有乘客报表已能按“今日 / 最近 7 天 / 最近 30 天”返回同车成员和账号的
  逻辑请求数、输入 Token、输出 Token、总 Token 及未知用量事件；界面目前主要以
  表格数字展示，没有限额和进度条。
- 现有管理端“用量报表”只有按车辆、用户或账号的聚合结果；数据库已保存
  单个逻辑请求的时间、请求模型、是否流式、结果、状态分类和安全原因码，以及
  实际用量事件的供应商、模型、各类 Token、是否已知用量、失败标记和状态分类。
- 现有 `usage-retention-days` 默认值为 90，后台每天分批删除过期的上游用量事件及其
  已结束逻辑请求；当前没有半年、一年、永久保留档位或管理员手动清理入口。
- CPA 上游不保证每次请求都返回用量，现有业务层已用 `usage_known` 区分
  “已知为零”和“未提供”。当 CPA 没有数据时，界面不能伪造精确值。
- CPA 现有上游账号原生配额是从响应中被动观测的账号级快照，目前只有
  Claude 和 Codex 存在已知观测协议。它不是按乘客分配的额度，也不保证每个账号都有值。
- 同级 `sub2api` 项目的主价格目录是 LiteLLM
  `model_prices_and_context_window.json` 的本地副本，基础单位为 USD/Token；其业务层另外处理
  模型别名、缓存读写、Service Tier、长上下文、图片及渠道自定义价格。
- `sub2api` 会从远程镜像更新价格目录，并在远程不可用时回退到本地副本。本项目为 MIT，
  只能参考其行为并基于 LiteLLM 数据格式独立实现，不直接复制 LGPL-3.0 业务代码。
- CPA 公共 usage 记录已携带实际上游模型、输入、输出、推理、缓存读取、缓存写入和
  Service Tier 等计价所需数据；现有拼车持久化只保存了合并后的缓存 Token，尚不足以精确复制
  `sub2api` 的缓存计价。
- 一次乘客逻辑请求可能因重试或切换账号关联多条 CPA 上游用量事件；两者不能作为同一种
  “请求数”平铺计数。CPA 当前没有稳定提供可展示的重试序号，界面不能自行虚构尝试编号。
- 拼车 Key 当前只允许 `internal/carpool/runtime/routes.go` 明列的 OpenAI、Claude、Gemini
  和 Codex 通用生成接口及模型查询；独立图片、音频、视频、Realtime 路由不在白名单内。
  通用生成接口仍可能携带多模态内容，不能仅凭路由名断言用量都是文本 Token。
- 升级前 `memberships` 没有限额字段，旧用量也没有价格快照，不能可靠还原历史美元费用。
  证据与已确认过渡规则见 `research/upgrade-transition.md`。

## 已确认需求

### R1 强制改密说明

- 保留密码重置后的强制改密安全门禁：乘客在完成改密前不能访问车辆、用量、
  账号状态或 API Key 功能。
- 强制改密页必须明确告知乘客：管理员已重置其登录密码；为保护账号，需先将
  临时密码更换为新密码；其车辆关系、用量记录和 API Key 没有被删除；改密成功后
  需使用新密码重新登录。

### R2 乘客限额与可见范围

- 上车限额为必填的有限 USD 金额，允许 0 或正数，不支持留空或“不限额”。`$0` 表示成员
  关系已建立但当前不能开始新的生成请求；管理员可通过后续调高限额立即恢复请求。
- 乘客实际消耗继续复用 CPA 已有用量事件，不从上游账号原生配额自动拆分或推算乘客限额。
- 乘客限额和已消耗金额统一使用 USD，管理端直接输入美元金额，乘客端使用 `$` 展示。
- 个人及同车当前成员用量使用金额进度条：分母为管理员设置的限额，分子为 CPA 用量对应的
  已确认费用。同车乘客公开各自限额、已确认金额、剩余金额、超额金额和进度，页面注明
  金额信息对同车成员可见；不得向其他车辆的乘客暴露成员或费用数据。

### R3 价格目录与冻结计价

- 模型价格与计价规则参考同级 `sub2api` 的 LiteLLM 目录并独立实现。
- 价格服务内置一份 LiteLLM 价格目录快照，默认每天从可配置的远程地址检查更新。远程下载、
  完整性校验或内容解析失败时，继续使用最后一份有效目录；不得用无效或半更新数据替换
  当前目录。离线环境仍可依靠内置或已缓存目录运行。
- 每条已计价用量事件保存所用目录版本或内容哈希、价格来源、各计价维度的实际单价和最终
  金额。目录更新只影响更新后开始的新请求，不重新计算历史事件；管理端显示当前目录版本、
  最近成功更新时间及更新失败状态。
- 每条可计价用量事件区分输入、输出、缓存读取、缓存写入及已支持的其他计价维度，
  保留实际模型；价格缺失及用量不足时的行为遵守 R6。

### R4 月度账期与成员历史

- 乘客限额按上车日每月自动重置。例如在报表时区的 9 月 12 日上车，第一个周期为
  `[9 月 12 日, 10 月 12 日)`，之后以每月 12 日为账期边界。上车日为 29、30 或 31 日且
  目标月不存在该日期时，当期边界截到目标月最后一日。
- 限额属于本次成员关系。首个账期从实际上车时刻开始，不按自然月 1 日起算；
  乘客离车或换车后，原成员关系的限额和历史消耗保留，新成员关系使用新的上车日和新限额，
  不携带旧车剩余额度。
- 限额账期按可配置报表时区计算，API 仍返回精确 UTC 半开区间 `[from, to)`，避免边界时刻
  被重复或遗漏计入。

### R5 请求限额与即时调额

- 限额采用后付费式硬限制：在一个新代理请求开始前，系统检查该成员本期已确认费用；当
  已确认费用大于或等于限额时，拒绝该乘客后续的新代理请求，且不连接上游。
- 已经通过限额检查并建立的请求继续使用请求开始时的授权快照完成。系统不在请求前估算或
  预留最大费用，因此最后一个请求和同时通过检查的并发请求可以使本期费用超过限额；界面
  必须如实显示超过 100% 的进度和超额金额，不截断为限额值。
- 管理员在账期中途修改限额时，新限额立即作用于当前账期。调高至高于本期已确认费用后，
  后续新请求立即恢复；调低至小于或等于本期已确认费用后，后续新请求立即被阻止。修改限额
  不重算历史费用、不改变当前成员关系的上车日或账期边界。

### R6 缺价、费用未知与范围

- 当请求的实际计价模型无法匹配可用价格时，系统必须在连接上游前拒绝该请求，返回可供
  客户端和界面识别的“模型价格未配置”错误；不得按 0 美元或猜测的相似模型价格放行。
- 当模型已有价格、但 CPA 或上游未返回 Token 用量时，该事件必须记录为“费用未知”，不得按
  0 美元计入已确认费用。此类未知费用不阻止后续请求；管理端和乘客端必须明确提示本期统计
  不完整，并显示费用未知的事件数量。
- 保留现有代理路由范围。模型列表与详情查询不消耗乘客限额；允许的生成请求复用 CPA
  可靠提供的 Token 计价数据。必要计价维度缺失时明确标记费用未知或统计不完整，不把不完整
  金额冒充完整费用；不新增非 Token 费用规则。

### R7 账号原生配额

- 账号进度条直接复用 CPA 提供的上游账号原生配额快照，并展示观测时间和上游重置时间
  （仅当 CPA 确实提供时）。供应商不支持、响应未携带或尚未观测到配额时，界面明确显示
  “上游未提供”，不以 0% 或 100% 代替；过期快照必须标记为陈旧。
- 同一账号的各个原生配额窗口分别展示，不能合并成一个百分比。前两个主要窗口直接展示
  独立进度条、已用百分比和可用的重置时间，其余窗口通过“展开全部配额”查看。仅提供额度
  状态而无百分比的窗口使用文字说明；缺失字段明确显示“上游未提供”。

### R8 管理端逻辑请求明细

- 管理端详细记录默认以一次乘客逻辑请求为一行，允许展开查看该请求关联的全部 CPA 上游
  用量事件。主行至少展示请求时间、乘客、车辆、API Key、请求模型、是否流式、最终结果、
  总 Token、总金额或“费用未知”；API Key 只展示安全名称和引用，不展示明文。
  展开项展示账号、供应商、实际模型、输入、输出、推理、
  缓存读取、缓存写入 Token、单次金额和状态。任何 CPA 未提供或无法可靠关联的字段均显示
  “上游未提供”，不得猜测或用 0 代替。
- 管理端详细记录沿用现有时间范围、车辆、乘客和上游账号筛选，并新增 API Key、模型、
  最终结果、计价状态以及 `request_id` 精确查询。模型筛选同时覆盖请求模型和上游实际模型；
  计价状态至少区分已计价、费用未知和因价格缺失而拒绝。
- 详细记录默认按请求开始时间倒序排列，以稳定游标每批加载 25 个逻辑请求，并通过
  “加载更多”继续查看；展开内容归属于主行，不作为额外分页记录。不用事件数量代替逻辑请求数，
  不伪造 CPA 未提供的重试序号。

### R9 保留策略

- 用量明细保留期支持 90 天、半年、一年和永久保留四档，默认 90 天；管理员还可以主动
  发起明细清理，且手动清理允许覆盖当前账期。自动与手动清理都必须采用有界批处理，并
  报告实际清理结果。
- 自动保留期只清理可展开的逻辑请求及上游事件明细，不自动删除精简账期汇总。账期汇总
  长期保留，直到管理员单独清理；已结束账期的汇总允许删除，当前账期汇总不能直接删除。
- 管理端新增“数据保留”设置页。配置文件中的保留天数只提供首次启用时的默认值；管理员
  在页面选择 90 天、180 天、365 天或永久后，将选择持久化到数据库并立即生效，数据库设置
  优先于配置文件。页面允许恢复为配置文件默认值。

### R10 手动清理与本期重置

- 数据保留页分别提供用量明细清理、已结束账期汇总清理和“重置本期用量”入口；执行删除前
  必须展示目标范围及预计数量，避免把用途和后果不同的操作混在一个按钮中。
- 普通手动清理只删除可展开的逻辑请求和上游事件明细，不改变当前账期用于限额检查的
  已确认金额及费用未知数量。管理员如需将本期累计归零，必须使用独立的“重置本期用量”
  操作；该操作需明确警告、二次确认并写入审计记录，且不改变限额或账期边界。

### R11 升级过渡

- 升级前已上车成员标记为“待设置限额”，暂停新的生成请求；管理员补设限额后按正常限额规则
  放行，设置为 `$0` 时仍不能开始新生成请求。保留原上车日和月度账期，不因补设限额而重置。
- 旧记录按保留策略继续可查，金额明确显示“历史记录未计价”，不按当前价格追溯扣减限额；
  仅对计价功能启用后的新请求计费，管理端与乘客端都注明金额统计覆盖起点。

### R12 全面界面重设计

- 2026-09-05 用户明确否决沿用旧样式的方案。重新设计拼车管理端、乘客端及登录/改密页，
  不以换色或在原有侧栏、统计卡与表格骨架上局部润色代替重设计。
- 通过 `qiaomu-design` 提供 A/B/C/D 四个真实交互方向样机，经用户选择后建立项目级
  `DESIGN.md`，再将选定设计应用于全部拼车界面。方向预览不是已完成的产品功能。
- 保持 R1 至 R11 业务约定、中文文案、权限隔离和现有功能完整；创意不得隐藏限额、金额、
  账期、数据缺失与危险操作后果。视觉方向尚待用户选择。
- 首屏明确请求是否可用、剩余金额与下次重置时间；管理员可高效进入成员调额与请求明细。

## 范围外与共同约束

- 不取消强制改密门禁，不改账号调度及跨车凭据隔离，不替代 `/management.html`。
- 不引入 `sub2api` 的充值、余额、渠道倍率、订阅、Redis 或扣款体系；不复制其 LGPL-3.0
  业务代码，不支持 CNY 换算、动态汇率或多币种配额。
- 不开放现有白名单以外的图片、音频、视频、Realtime 等路由，仍返回 `route_not_supported`；
  不新增非 Token 计价规则，不提供全文搜索或 CSV 导出。
- 不展示或持久化提示词、响应正文、原始上游错误体、密钥或上游凭据。所有管理写入继续执行
  角色、Origin 与 CSRF 校验，历史明细仅使用安全快照和公开引用。
- 保留原生 JavaScript 和 Go 内嵌静态资产交付，不为视觉重设计强制引入前端构建系统；
  现有样式与布局不再是约束，CPA 本体 `/management.html` 不在重设计范围内。

## 验收标准

- [ ] 四方向样机具有字体角色、明暗/时代、布局与密度的实质差异，可调拨盘并确认回传。
- [ ] 全部拼车页面遵循用户选定的 `DESIGN.md`，不保留旧样式与布局骨架；桌面和移动端
  检查无文字遮挡、整页横向溢出或不可达操作，旧功能与业务权限无回归。
- [ ] 管理员重置乘客密码后，旧网页会话失效；乘客使用临时密码登录时，只能执行
  改密和退出登录。
- [ ] 强制改密页清楚说明重置原因、强制改密的目的、业务数据仍保留，以及改密后需
  重新登录；不得以空白页或只有表单而无说明的方式展示。
- [ ] 乘客改密成功并使用新密码重新登录后，恢复看到改密前的车辆、成员、账号、
  用量和 API Key 数据。
- [ ] 对于 CPA 确实观测到原生配额的账号，乘客端按上游窗口展示账号用量进度、观测时间和
  可用的重置信息；对于没有可用快照的账号，显示“上游未提供”而不伪造进度。
- [ ] 同一账号具有多个原生配额窗口时，两个主要窗口直接显示，其余窗口可展开查看；每个
  窗口保持独立百分比和重置时间，没有百分比时只显示上游已提供的状态文字。
- [ ] 乘客进度只使用管理员配置的乘客限额作为分母，使用 CPA 的实际用量事件作为消耗数据；
  不会把整个上游账号的配额当作某一名乘客的限额。
- [ ] 乘客可查看同车所有当前成员的限额、已确认金额、剩余或超额金额及进度条，页面明确说明
  金额信息在车内共享；任何乘客都无法查看其他车辆的成员或费用数据。
- [ ] 管理端和乘客端均以 USD 显示乘客限额、已用金额和剩余金额，同一份数据在两端的
  进度百分比与金额一致。
- [ ] 管理员未填写限额或输入负数、无限值及无效金额时无法上车；输入 `$0` 可建立成员关系，
  但该成员的新生成请求立即被额度检查拒绝，调高后无需重新上车即可恢复。
- [ ] 不同上车日的两名乘客使用各自的月度账期；在账期边界前后的用量分别进入正确周期，
  29、30、31 日上车、时区偏移和夏令时场景不会重计或漏计。
- [ ] 乘客离车或换车后，旧成员关系下的账期、限额和历史金额仍可由管理员核对；新车的
  使用从新上车日和新限额开始，不携带旧车剩余额度。
- [ ] 当某乘客本期已确认费用低于限额时，新请求可正常开始；达到或超过限额后，新请求在
  连接任何上游前被拒绝，并返回可供客户端和界面识别的额度耗尽错误。
- [ ] 已经开始的请求不会因随后达到限额而中断；最后一个请求或并发请求造成超额时，管理端
  和乘客端均显示真实已用金额、超过 100% 的进度与超额金额。
- [ ] 管理员修改当前成员关系的限额后，新值立即用于后续请求检查：调高到已用金额以上可立即
  恢复请求，调低到已用金额以下或相等时立即阻止新请求；历史费用及账期锚点保持不变。
- [ ] 请求模型没有可用价格时，请求在连接任何上游前被拒绝，并返回“模型价格未配置”错误；
  系统不会使用 0 美元或相似模型的猜测价格放行。
- [ ] 模型查询不增加乘客已用金额；现有允许生成路由的可靠 Token 用量参与金额计费，
  必要计价维度缺失时显示费用未知或不完整；图片、音频、视频、Realtime 等当前不支持的
  独立路由仍以 `route_not_supported` 拒绝，本次变更不会扩大访问范围。
- [ ] 服务可从可配置远程地址每日更新价格目录；更新失败或内容无效时保留最后有效版本，
  首次离线启动可使用内置快照，不因远程不可用而丢失已有模型价格。
- [ ] 每条已计价事件可核对目录版本、价格来源、实际单价和计算结果；价格目录更新后，已有
  事件的金额保持不变，只有后续新请求使用新价格。管理端可查看当前价格版本和更新状态。
- [ ] 模型有价格但 CPA 或上游未返回 Token 用量时，用量事件记为“费用未知”而非 0 美元，
  后续请求仍可继续；管理端和乘客端均提示本期统计不完整并显示费用未知事件数。
- [ ] 管理端每条明细主行只计一次乘客逻辑请求；同一请求发生重试或切换账号时，关联的上游
  用量事件在该行内展开显示，不会被误计为多次乘客请求。
- [ ] 明细主行和展开项包含已确认的请求、身份、模型、结果、Token 与金额字段；CPA 未提供的
  值明确显示“上游未提供”，页面不展示提示词、响应正文、原始错误体或任何密钥与凭据。
- [ ] 管理员可按时间、车辆、乘客、上游账号、API Key、模型、最终结果和计价状态筛选明细，
  也可按完整 `request_id` 精确查询；组合筛选只返回同时满足条件的逻辑请求。
- [ ] 明细按请求开始时间稳定倒序，每批加载 25 个逻辑请求；继续加载不会重复或遗漏主行，
  一个主行下的上游事件不会占用额外分页名额。
- [ ] 第一阶段界面不提供全文搜索或 CSV 导出。
- [ ] 用量明细保留期可设置为 90 天、半年、一年或永久，默认 90 天；非永久档位按所选期限
  自动清理明细，永久档位不执行基于年龄的自动清理。
- [ ] 自动清理明细后，精简账期汇总仍可用于核对旧成员的账期区间、最终限额、已确认金额、
  费用未知数量和超额金额；已结束账期汇总只会被管理员通过独立操作主动删除。
- [ ] 管理员可手动发起历史用量清理，操作有明确范围、确认提示和清理结果，不会因一次请求
  无界删除大量数据或长时间独占数据库。
- [ ] 管理端“数据保留”页可选择 90 天、180 天、365 天或永久，保存后立即作用于后续清理；
  数据库中的选择优先于配置文件，也可恢复使用配置文件默认值。
- [ ] 数据保留页将明细清理、已结束账期汇总清理与本期用量重置明确分开，每项操作在确认前
  显示目标范围、预计数量及不可逆影响，并在完成后显示实际处理数量。
- [ ] 管理员可将当前账期纳入手动清理范围；界面必须在确认前明确说明清理后对本期已用金额
  和后续限额拦截的影响。
- [ ] 普通清理当前账期明细后，乘客本期已确认金额、费用未知数量及限额拦截状态均不改变。
  “重置本期用量”是独立操作，二次确认后归零本期限额累计且留下可核对的审计事件，但不修改
  本期限额、上车日或账期边界。
- [ ] 升级前已有成员显示“待设置限额”且不能开始新生成请求；管理员补设正数限额后按限额
  规则恢复，补设 `$0` 仍阻止生成请求，原上车日及月度账期均不改变。
- [ ] 升级前旧记录保留原有 Token 和结果数据，金额显示“历史记录未计价”而非 `$0`；
  不追溯扣减限额，两端均明确显示金额统计仅覆盖计价启用后的新请求及其覆盖起点。
