# 用户多周期额度与账号及用户并发限制

## 状态与目标

状态：用户已批准最终方案并明确“开始”，当前正在实施与验收。目标是在现有拼车月额度之上增加与上游账号同步的用户 5h / 7d 金额额度，以及可排队的用户、账号并发限制，避免单用户占满账号并保留可理解的用量展示。

## 背景与证据

- 用户额度目前采用 `MonthlyLimitNanoUSD` 与 `monthly_limit_usd`；`internal/carpool/store/sqlite/authorization.go:112` 根据月账期已确认费用拒绝新请求。月账期按上车时间锚定。
- `internal/carpool/runtime/quota_projection.go` 已有逐账号 Claude 5h/7d、Codex 主次窗口投影和可选 `ResetAt` / `WindowMinutes`，不等同于用户金额额度。账号重置时间可能缺失。
- `sdk/cliproxy/auth/quota_signals_test.go` 覆盖业务响应头更新观测与无信号时保留旧快照；缺少周期就拒绝所有请求会妨碍首次或新周期观测。
- `sdk/cliproxy/auth/home_concurrency.go` 有 Home 凭据并发协议，`config.example.yaml:72` 明确其策略由 Home 管理；`internal/carpool/service/control.go:1513` 所属授权路径当前拒绝 Home，因此不是拼车本地限制的实现。
- `internal/carpool` 尚无用户/账号请求并发准入；车辆结构支持多账号，但用户本轮明确限定一车一账号。
- 历史契约见 `.trellis/tasks/archive/2026-09/09-05-passenger-billing/prd.md`：已开始请求继续并可超额，不重引入复杂租约或崩溃精确恢复机制。
- 接入证据和风险见 `research/integration-evidence.md`。

## 需求与验收

| 编号 | 需求 | 可观察验收 |
| --- | --- | --- |
| R1 | 保留月额度；新增用户 5h / 7d USD 额度 | 管理员可单独读取、设置、取消两种新增额度；金额精度与月额度一致，零表示零额度，负数/非法金额拒绝；原月接口兼容 |
| R2 | 用户短周期直接跟随车辆唯一账号实际周期 | 同车用户的对应重置时间一致；收到相同周期重复观测不清零；原上车时间不再作为新增周期锚点；5h 与 7d 分别同步，不互相重置 |
| R3 | 新增四项限制独立配置，未配置表示不限制 | 旧数据升级后月额度仍有效，不因新增字段为空阻断；修改新增额度或并发上限不影响其他限制 |
| R4 | 周期未知时暂不执行对应短周期限制 | 页面显示“周期待同步”，不伪造零用量或重置倒计时；月额度、并发和同步记账失败门禁继续生效；已有未结束的有效周期继续使用 |
| R5 | 费用沿用同步记账与去重契约 | 同一真实费用同时参与适用的月、5h、7d 校验，但账单实际费用只记一次；已确认达额拒绝新生成，已开始请求继续；重复事件、重启、普通清理不能清空有效累计 |
| R6 | 增加用户与账号请求并发上限 | 用户多个 API Key 共享用户上限；同一账号服务多个用户共享账号上限；流式请求持续占用直到结束；内部重试不重复增加逻辑请求名额 |
| R7 | 并发不足时进入有界队列 | 未获名额不得调用上游；只有队列满才以队满原因返回 HTTP 429；等待者取消立即退出；不得无限积压或持有部分名额等待另一类名额 |
| R8 | 出队重新校验，正确释放资源 | 出队时重查身份、Key、成员/账号授权、费用额度与记账健康；失效请求不执行；成功、失败、无效正文、取消和流结束无名额泄漏；不强杀在途请求 |
| R9 | 保持现有界面并补齐状态 | 管理端可配置新增四项限制；用户端可看到对应额度、已知用量、剩余、重置时间、未知周期状态及自己的并发上限；中文文案和既有视觉风格保持一致 |
| R10 | 单实例内保持稳定隔离与兼容 | 限制不按 API Key 或瞬时分配记录拆分；普通模型查询不占新增生成并发；旧全局 Key、Home、未开放协议不扩展；历史记录和价格不追溯重算 |

## 已确认关键决定

- 周额度按 7d 理解，不新增 7 小时额度。
- 采用实际账号周期，取代此前上车时间锚点；当前一车一账号，不增加基准账号选择。
- 周期待同步期间允许对应短周期保护空档，不改变月额度与并发限制。
- 并发不足可以排队；用户最新决定覆盖此前“直接 429、不排队”方案；等待队列必须有容量上限，队满返回 429。

## 最终批准的落地值与边界

以下随最终方案及默认队列容量 10 的修订获准实施：

- 单进程拼车等待队列默认最多 10 个请求（默认值已由用户明确指定），提供配置调整容量；不设额外排队超时，客户端取消或服务关停时退出。
- 用户与账号并发上限仅接受正整数或“不限制”；暂停服务沿用现有禁用能力，不把零并发做成永久等待。
- 等待队列优先放行最早满足双方并发条件的请求，避免单个用户阻塞其他可执行用户。
- 账号更换后跟随新账号周期，历史费用不删除、不改价；同一 AuthID 重新分配不得凭分配 ID 变化清零累计。新账号首次观测或统计覆盖不足需明确展示，不承诺跨账号额度连续折算。
- 新周期统计从功能启用后的可靠费用记录开始，不为旧的未计价历史补造费用；周期暂缺期间的新费用保留，获得有效边界后归入对应周期。
- 本轮只限制当前单实例的拼车生成请求，不统计旧全局 Key 或外部客户端直接使用上游账号的并发；不做跨实例分布式限制。
- 现有管理员“重置本期”保持月账期操作，不自动清空新增短周期；界面需明确月周期范围，避免歧义。

## 不在本轮范围

- 多账号车辆的周期协调、基准账号选择、用户×账号独立额度及强制变更现有账号分配数量约束。
- 修改上游原生额度、按上游百分比自动推算用户 USD 上限、分布式限流或 Home 新接入。
- 新增充值、余额、订阅、持久化队列、租约树、跨账号历史账单重算及崩溃精确费用恢复。
- 全面 UI 重设计、扩大协议支持或独立 translator 重构。

## 风险与交付门禁

- 上游周期信息缺失可能持续，期间对应限制不生效是已接受风险；界面必须准确提示。
- 费用事后确认，已开始的并发请求可产生超额；额度不是预扣余额。
- 等待请求占用 HTTP 连接，队列容量不等同于全进程内存上限；客户端或外层代理仍可能自行断开。
- 规划文档与上下文清单已完备，用户已批准并执行 `task.py start`；测试、独立检查与规范更新通过后再提出提交计划。
