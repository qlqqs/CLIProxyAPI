# 已撤销的复杂结算候选方案

2026-09-14 用户否决过多兜底。本文件仅保留决策历史，不是实施或检查要求。

## 2026-09-14 第二轮：可靠结算设计补充（待确认）

### 已核实的问题归属

1. `sdk/api/handlers/handlers_stream.go` 的 HTTP 完成早于插件流用量发布，取消时也不能
   证明 executor 的所有用量生产者都已退出。仅调整一个 defer 顺序不足以覆盖整个生命周期。
2. `accounting.Writer.pending` 没有容量限制；故障时模型查询完成事件仍可积累。
3. 自动清理和显式清理都以 HTTP `outcome` 判定是否可删，没有独立账务结算保护。

### 拟定的修改边界

- 允许在现有子任务内新增递增迁移，保留 `001` 至 `003` 内容与 checksum。
- 增加独立于 HTTP outcome 的持久化结算状态。上游开始前留下未结算事实；只有用量
  生产者全部结束且已发生记录成功持久化，才能改为已结算。SDK 只携带可选服务器
  观察契约，不导入拼车业务；未启用拼车的请求仍走原路径。
- 启动核对根据结算状态，不再只查询 `outcome=incomplete`；不能把已终态且账务未
  结算的请求当作安全完成。旧数据升级必须明确区分历史记录和无法证明已结算的记录。
- 内存失败缓冲需要同时定义记录数和单项大小约束。非计费模型查询完成与计费重试
  隔离，避免查询请求不断占用计费故障缓存。不能在 slice 满时丢弃已发生费用。
- 自动清理、显式明细清理、已结束账期删除都使用同一账务结算保护条件，保留未核对
  的请求、事件、scope 和账期；预览与执行必须一致，恢复不能依赖可删除的显示记录。
- 核对恢复必须有受控、可审计的过程，不能要求用户通过随意改 outcome 或删库解锁。
  具体恢复入口及升级分类在容量行为确认后继续收敛；不在本轮引入 UI 重设计。

### 已确认的故障行为（2026-09-14）

用户已接受缓冲达到上限时施加背压：暂停继续发布/完成，等待存储恢复和成功落库，保留取消
后的已发生用量；不设置新的上游超时，不因额度变化中断已放行请求。其代价是存储长时间
故障时，已放行请求可能延迟结束，关停仍需明确报告未排空。

不能用无界等待 goroutine 伪装有界缓存：实施前还需核对发布者数量、数据所有权和唤醒
策略；测试须证明总保留数据有界且恢复不会死锁。若业务要求故障时仍立即结束响应，则
需要额外可靠落盘介质及相应磁盘故障语义，属于另一种设计，不能默认引入。

本段是待确认方案，不授权第二轮产品代码实施。价格目录冻结、缺价前置、前端仍不在
本轮范围；既有数据库不执行生产迁移，不提交或归档。

## 第二轮最终候选方案：生产者所有权与持久化结算

### 调研收敛

详见 `research/settlement-producer-lifecycle.md` 与 `research/settlement-storage-plan.md`。
流输出 channel 关闭不证明底层生产者结束；一些 provider、插件调用和取消分支仍能在
HTTP completion 后发布。因此必须覆盖实际异步生产者，不采用“改一个 defer”的修补。
本轮仅覆盖现有拼车允许路径及其内部 provider；Home、外部 WebSocket、Realtime 等
既有禁用路径不因此放开，也不为不可达路径做无关改造。

### 可选 SDK 所有权契约

- 授权成功、实际执行前创建服务器持有的根作用域。HTTP 结束释放根拥有权；已登记
  的 provider/插件孩子在真实退出前持有自己的租约，允许期间登记孙孩子。
- `Fork` 与 `Release` 原子协调；已释放父租约不能重新登记，不能靠裸 WaitGroup 的
  Add/Wait 竞态推断完成。每个子租约在启动 goroutine/回调前登记，最后一次同步用量
  持久化或有界队列所有权转移后归还。
- 只有根与全部孩子退出、已发生事件全部确认、网络完成事实已保存，才触发恰好一次
  账务结算；结算回调在作用域锁外执行，不能等待自己或尚未派发的完成插件。
- 公共 SDK 只提供可选生命周期接口，provider helper 放 `internal/runtime/executor/helps/`。
  不修改 Token 解析/translator，不改变旧全局 Key 路径；SDK 可选接口缺失时 no-op。
- 不能合作登记的后台插件工作，必须在上游前拒绝从已关闭作用域启动新计费执行，
  不允许先发生费用再拒收事件。未知完成信号保持 pending，不猜测 settled。

### 容量与背压

- 使用模块级请求/生产者容量预留，在上游执行前取得，未开始工作在容量耗尽时直接
  返回安全 503；不先创建无限量等待者。新限制仅作用于拼车计费路径。
- 候选默认值：最多 512 个计费根/活跃生产者总槽、单请求最多 32 个活跃子生产者、
  嵌套深度最多 16；通过内部配置/测试注入表达，不在本轮扩展前端。最终代码需明确
  根与 producer 的独立计数，测试证明不会超预算或因父持有槽而等待孩子死锁。
- 已发生事件每个 producer 最多一个同时等待的发布，使用自己已预留的容量；固定
  512 条安全事件缓冲，达到上限后按用户已接受行为等待成功落库。采用一个受控
  重试驱动，不按事件新建 goroutine，不以新上游超时结束等待。
- 安全事件字段只保留固定计量及有界身份/模型信息；执行前检查必要标识长度，已经
  发生费用后不能因字段超长而静默丢弃。必须报告并测试实际字节上限，而非只限制条数。
- 非计费模型查询完成不进入计费故障队列；其原记录可靠性单独处理，不能持续占用
  金额缓冲，也不能绕过查询原有授权。
- 保证范围是计费故障缓存及其等待生产者，不声称整个服务器内存有界；旧全局 usage
  异步队列和 provider 正文缓存不在本轮重构范围。

### 升级与清理

采用存储侧文档中的递增 004 迁移与独立状态，pending 与网络 outcome 解耦。无证据
证明结算完整的旧计费记录保守进入待核对；这可能在升级后继续阻止拼车生成，最终交付
必须说明，不能把“状态迁移成功”当作可上线依据。既有历史无账期、明确非计费和本地
授权拒绝单独分类，不能假设所有旧终态都安全，也不能追溯按新价格收费。

自动/显式清理、预览与账期删除保护相同未结算状态；本期重置不能解除核对门禁。
本轮不新增随意解锁按钮或手工 SQL 恢复指南。崩溃丢失内存事件无法精确重放的情况
继续待核对；审计化对账恢复入口另行规划，不用“未知等于零”换取自动恢复。

### 范围与验收门禁

本轮允许修改相关 provider/插件生命周期、SDK、拼车存储/迁移/授权/清理及测试；
不改价格冻结、缺价拦截、前端，不自动提交或归档。先建立确定性反例，再串通迁移和
生命周期，最后接容量/背压、清理并做独立审查。

验收必须证明：终态后发布失败并重启仍封锁；正常完整请求可结算且不误封锁；满容量
恢复不丢账、不无界增长、不死锁；所有清理都无法清除核对依据；旧 Key 保持行为。
运行定向与 race、全量 test/vet、正常和无 CGO 构建。只有这些门禁通过，才能将三个
P1 标为关闭；对账恢复工具和父任务其他缺口仍保持未完成。

此方案已完成代码调研，等待用户对扩大后的修改范围、容量限制及保守升级风险确认。
用户此前接受背压不等同于批准本节所有新增范围，因此确认前不派发第二轮实现。

改按最小行为缺口重新收敛：保留同步记账和运行中数据库失败拒绝新生成；优先修正已知
用量发布与 completion 顺序，隔离非计费查询，限制计费故障缓存，保护明确未完成事实。
不承诺进程崩溃后的精确账务恢复；是否允许重启后仅标记不完整而不全局封锁，仍需用户
确认。既有第一轮启动封锁代码尚未撤回，不得把规划变化说成代码已经变更。
