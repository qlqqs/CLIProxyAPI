# 独立结算与清理保护：存储侧设计依据

## 本轮代码事实

- `migrations/002_billing.sql` 为 `proxy_requests` 添加账期、价格状态和金额字段，尚无
  独立结算状态。`003_retention.sql` 的事件账期外键意味着删除账期时也要保护相关事件。
- `AuthorizeAndBeginProxyRequest` 在同一事务创建请求与 scope，适合在任何上游调用前
  持久化未结算状态；鉴权失败回滚不应留下孤立的账务占位。
- `RecordUsageEventBilled` 已把事件和汇总同事务写入并按事件 ID 去重，可复用；不能
  因新增结算状态改成异步扣额或重算历史金额。
- `HasUnreconciledBillingRequests` 只查 `outcome=incomplete`，无法保护已终态后迟到用量。
- `CleanupRetention`、`PreviewRetention`、`ExecuteRetention` 都只按网络终态判定可删。
  不仅请求，关联事件、scope 和整个账期都必须受到结算约束。

## 建议持久化契约

新增 `004_accounting_settlement.sql`，保持之前迁移及 checksum 不变。
为请求添加独立 `settlement_state` 与修订字段/必要索引，状态为：

- `not_required`：明确非计费的模型读取、授权拒绝、启用计费前的历史记录。
- `pending`：已授权，仍可能有用量生产者，或已发生事件尚未成功落库。
- `settled`：生产者结束、全部事件持久化且网络完成事实已保存。
- `reconciliation_required`：进程中断或不可恢复异常，无法证明账务完整。

结算状态不覆盖 `billing_status`；已结算请求也可能费用未知。账务完整性是有无遗失
生产事实，费用完整性是上游信息能否计价，两者不得混用。

`pending` 在授权同事务创建；`settled` 只能由服务器持有的生产结束证明触发，并与
待写事件的处理顺序协调。不能仅凭 HTTP completion 或“当前计数等于零”提前结算。
在启动提供 HTTP 服务前，将遗留 pending 归为待核对并保留跨重启门禁。

迁移旧记录时，不能依据 outcome 成功或已有费用猜测结算完成。既有计费请求中不能
证明结算完整的记录保守归为待核对，不按当前价格追溯计价；该保守升级行为须在最终
摘要说明。没有 scope/账期的历史记录不能被误认为新账务失败。

## 清理契约

只允许删除 `not_required` 或 `settled` 且满足原时间/终态限制的请求与事件。
账期只在其引用请求全部可清理/已结算时删除；不能先置空引用后绕过状态检查。
预览与执行复用相同筛选，执行事务内重查，返回受保护条目计数而不是冒充成功删除。
本期 reset 不代表结算或核对完成，不能清除门禁和待核对状态。

不能把显示记录删除作为人工核对完成操作；本轮不提供直接改状态解锁接口。
受控对账恢复工具属于后续明确交付：必须有可验证费用依据、幂等更新和同事务审计，
不能把缺失账单默认为零。若因这个限制不能上线，应如实保留未完成状态。

## 定向验证

- 旧库升级保留全部事件/金额/锚点，重复启动不改变状态分类和启用点。
- HTTP 完成后新事件失败，再重启仍阻止生成；已完整结算请求不误封锁。
- 模型读取、旧全局 Key 与拒绝请求不会成为计费 pending。
- 自动/手动清理和账期删除不能移除 pending/待核对事实，预览与执行一致。
- 清理后重启不能使门禁消失；重置金额不能绕过待核对保护。
- 所有测试使用隔离 SQLite，不修改用户现有数据库。
