# 拼车用户管理第一阶段

## 目标

将 CLIProxyAPI 扩展为由管理员运营的单实例拼车服务：管理员可以创建用户和
车辆、设置车辆席位、把乘客与一个或多个上游账号手动分配到车辆；乘客可以
登录、使用自己的 API Key 调用兼容代理，并查看本车成员的聚合用量以及本车
账号的安全状态和用量。

第一阶段的核心价值是让多个用户安全共享一组上游账号，同时保证车辆之间的
账号隔离、凭证隔离、历史归属和最小必要可见性。

## 角色与术语

- **CPA 管理员**：持有现有 Management API 密钥，继续管理 OAuth、上游
  凭据、模型和底层配置。
- **拼车管理员**：登录 `/carpool/` 后管理用户、车辆、成员关系、上游账号
  分配和聚合报表，但不会因此获得现有 Management API 权限。
- **乘客**：登录 `/carpool/` 查看当前车辆，并使用独立用户 API Key 调用
  获准的代理 HTTP 端点。
- **上游账号**：现有凭据管理器中的稳定 `AuthID` 所代表的 OAuth 或 API Key
  凭据。浏览器中只显示独立的安全引用与管理员配置标签。
- **当前关系**：尚未写入终止时间的成员关系或账号分配；历史关系不会物理
  删除。

## 背景与确认事实

- CLIProxyAPI 已有 OpenAI、Gemini、Claude、Codex 兼容端点、入站 API Key
  鉴权、上游凭据池、重试、冷却、故障转移、会话亲和、管理 API 和用量事件。
- 当前项目没有业务用户、网页登录会话、车辆、成员关系、车辆账号分配或可供
  乘客查询的持久化用量库。
- 当前短期用量队列会过期且读取后删除，不能充当历史报表事实源。
- `/management.html` 来自独立前端仓库的远程构件，本仓库不包含其应用源码。
- 用户已经确定采用“CPA 进程内模块化二开 + 独立 `/carpool/` 前端入口”，
  第一阶段保留 `/management.html`，不 fork 现有管理前端。
- 用户已经确定使用 SQLite，第一阶段限定单机、单 CPA 实例，不部署
  PostgreSQL 业务库。
- 用户已经确定第一阶段由管理员手动分配，不提供乘客自助上车、下车或换车。
- 用户已经确定每名乘客最多属于一辆当前车辆，每个上游账号最多分配给一辆
  当前车辆。

## 第一阶段范围

### R1：用户身份与网页登录

- 系统必须支持 `carpool_admin` 与 `passenger` 两类拼车用户，并使用全局唯一、
  大小写规范化的用户名登录。
- 用户角色在创建时确定，第一阶段不可修改。`carpool_admin` 不能拥有车辆成员关系、
  创建用户代理 Key 或使用用户 Key 调用代理；需要乘车的管理员必须使用独立乘客
  账号。
- 首个拼车管理员必须通过一次性 CLI 交互创建；不得存在默认管理员或默认密码，
  不得通过命令行参数或日志传递明文密码。
- 密码必须使用带随机盐、参数可升级的强密码哈希保存；数据库不得保存或返回
  明文密码。
- 登录成功后签发服务端可撤销的不透明会话 Cookie。Cookie 必须为
  `HttpOnly`，生产配置为 `Secure`，使用 `SameSite=Strict` 和 `/carpool/` Path。
- 会话绝对有效期和空闲有效期可配置，默认分别为 24 小时和 2 小时。每次请求
  都必须校验会话、用户状态和角色。
- 修改或重置密码必须撤销该用户全部网页登录会话；默认不撤销用户 API Key。
  管理员必须能显式撤销该用户全部 API Key。
- 禁用用户后，其全部会话和用户 API Key 对新请求立即失效；重新启用不会复活
  已撤销的会话或 Key。
- 登录接口必须执行 Origin 校验和限速；Cookie 鉴权的其他状态变更接口必须执行
  Origin 与 CSRF 双重校验。缺失、`null` 或不受信 Origin 一律拒绝，失败响应不能
  泄露用户名是否存在。多个浏览器标签页必须能共享同一会话的 CSRF 状态，页面
  刷新不得导致其他标签页无故失效。

### R2：用户 API Key 与凭证域

- 乘客程序化请求必须使用独立生成的用户 API Key，不得使用网页登录 Cookie
  访问代理端点。
- 用户 Key 必须采用版本化保留前缀和高熵随机秘密，明文只在创建时显示一次；
  数据库只保存非敏感查找标识和秘密摘要。
- 乘客能够命名、创建、查看元数据、单独撤销和轮换自己的 Key；管理员能够
  查看非敏感元数据并撤销单个或全部 Key。Key 可设置过期时间，第一阶段不固定
  每用户数量上限。
- 第一阶段“轮换”定义为先创建新 Key、确认客户端切换后再撤销旧 Key；不提供
  自动替换旧 Key 的专用原子端点。
- 管理密钥、拼车 Cookie、用户 API Key、旧全局 `api-keys` 四个凭证域不得
  互相替代。拼车用户 Key 的保留前缀不得被配置成旧全局 Key。
- 旧全局 Key 保持现有代理行为，但没有用户或车辆身份、不能访问
  `/carpool/api/*`，也不进入拼车用户、车辆或账号报表。
- 用户 Key 必须兼容现有协议使用的 Bearer、`X-Api-Key`、`X-Goog-Api-Key` 和
  既有查询参数凭证位置，但只接受保留前缀。启用拼车后，代理入口必须先汇总所有
  凭证位置；相同值可去重，出现两个不同值时在任何 provider 认证前拒绝，不能按
  provider 顺序择一。启用拼车后不再保留“没有任何凭证也可访问代理”的匿名旧
  行为；调用方必须使用用户 Key 或已配置的旧全局 Key。
- 第一阶段不允许拼车鉴权与声明为 exclusive 的第三方前端鉴权插件同时启用；
  配置冲突必须在启动时失败，不能悄悄绕过拼车 provider 或改变插件独占语义。

### R3：车辆、席位与成员关系

- 拼车管理员能够创建、查看、修改、启用、禁用和退役车辆。
- 车辆可以设置可选的正整数 `seat_limit`；未设置表示不限制。达到上限后新增
  或换入成员返回冲突，降低上限到当前人数以下也返回冲突，不隐式移除用户。
- 拼车管理员能够创建、查看、修改、启用和禁用用户，并手动加入、移除或换车。
- 只有乘客能够拥有当前成员关系；每名乘客最多有一个当前车辆。并发分配也必须
  保持这一约束。
- 成员关系使用开始和终止时间保留历史。换车必须原子地结束旧关系并建立新关系；
  换车前的用量仍归属旧车辆。
- 当前同车成员使用管理员配置且车内唯一的 `display_name`。该字段是公开展示名，
  不要求是真实姓名，不得自动回退为登录名或邮箱。
- 禁用车辆后，乘客不能访问其面板数据或发起新的代理请求；已建立上游连接的
  请求不强制中断。退役车辆不能再接收新成员或账号，但历史仍可由管理员查询。

### R4：车辆上游账号分配

- 拼车管理员能够从当前凭据管理器中选择现有上游账号，为车辆分配一个或多个
  账号、撤销分配或执行账号移车。
- 每个上游 `AuthID` 最多只有一个当前车辆分配；并发分配也必须保持这一约束。
- 账号分配必须要求管理员提供不含敏感信息的 `safe_label`，并生成仅供业务 API
  使用的 `account_ref`。乘客响应绝不能返回完整 `AuthID` 或原始凭据标签。
- 账号移车必须原子地结束旧分配并创建新分配。移车前的请求及用量仍归属旧车；
  新请求只能从新车使用该账号。
- 上游凭据从运行时消失时不得级联删除历史分配。当前分配在乘客视图中显示为
  `unknown` 或 `unavailable`，且不能被新请求选择。

### R5：代理隔离与协议范围

- 用户 API Key 的每个逻辑请求必须在请求开始时解析并固化用户、Key、当前成员
  关系、车辆和允许的 `AuthID` 集合；客户端不能提供或扩大该集合。
- 初次选择、重试、故障转移、模型回退、快速/传统调度、插件调度和会话亲和都
  只能在固化集合与当前可用候选的交集中选择。任何范围外结果都必须默认拒绝。
- 无有效用户、有效 Key、当前成员关系、启用车辆或允许账号集合时，必须在连接
  上游前拒绝；响应不得泄露其他车辆的账号数量或状态。
- “请求开始”定义为用户 Key 已认证、授权结果已固化且逻辑请求事实成功提交。
  此后即使尚未连接上游，普通 HTTP 请求也可使用该不可扩张快照完成；运行时
  全局禁用、模型不匹配或冷却仍可继续缩小候选。管理事务提交后才开始的请求必须
  使用新授权，请求期间新分配的账号不能加入原快照。
- 第一阶段用户 Key 至少支持通过隔离测试的 OpenAI Chat/Completions/Responses
  HTTP、Claude Messages HTTP、Gemini Generate/Stream/Interactions HTTP 以及
  相应模型查询；实际开放端点必须由显式白名单控制。
- Responses WebSocket、Realtime、wsrelay、Home 调度以及任何尚未通过完整隔离
  测试的入口必须明确拒绝用户 Key。旧全局 Key 在这些入口保持现有行为。
- 拼车改动不得改变已支持协议的响应形态、流式 framing、取消、重试、冷却和
  供应商翻译行为。

### R6：乘客可见性与账号状态

- 乘客只能查询自己的当前车辆，不能枚举其他车辆或历史车辆。
- 乘客必须能查看当前成员列表和“今日”“最近 7 天”“最近 30 天”三个周期的
  成员聚合用量；服务端必须返回实际 UTC 半开区间，展示时使用可配置报表时区。
- 每名成员的乘客视图只显示 `display_name`、当前/已离车状态、逻辑请求数、
  成功/失败数、已知 Token 合计和未知用量数。不得显示登录名、邮箱、内部 ID、
  单请求时间线、模型明细、提示词、响应或原始错误。
- 乘客必须能查看本车账号的 `account_ref`、`safe_label`、供应商、安全状态、
  `observed_at`、`stale` 和同周期安全用量汇总。
- 安全状态枚举固定为 `healthy`、`degraded`、`unavailable`、`disabled`、
  `unknown`。状态来自现有运行时观测，不因页面查询主动探测上游；观测超过
  5 分钟必须标为陈旧，未知不能显示为健康。
- 页面最多每 60 秒自动刷新状态；刷新失败保留上一结果并明确显示陈旧或错误，
  不能伪造正常状态。

### R7：用量与管理员报表

- 系统必须分别持久化逻辑请求终态与实际上报的用量事件，并以稳定请求 ID 关联。
  逻辑请求数不得因重试而重复累计。
- 逻辑请求至少区分进行中、成功、失败、授权拒绝、取消和崩溃后不完整；覆盖已
  开放用户 Key 入口的非流式、HTTP 流式、无可用账号和客户端中断路径。
- 无法验证、已撤销或已过期的 Key 不属于已认证逻辑请求，只写入不含明文身份的
  安全审计。Key 已成功认证但用户被禁用、无成员关系、车辆不可用、账号集合为空
  或路由不受支持时，必须生成恰好一条可空车辆归属的 `rejected` 请求事实和安全
  `reason_code`，且不连接上游。
- 用量事件必须保存实际选中的上游账号归属以及输入、输出、缓存、推理和总 Token
  的可空值，并明确保存 `usage_known`。未知用量不能写成已知零。
- 若同一逻辑请求的多个上游尝试都产生实际已知 Token，Token 汇总包含全部实际
  消耗；乘客请求数仍只计一次。第一阶段数据不得宣称为账单或严格一次计费事实。
- 用户、成员、车辆或账号换车后，不得改写请求开始时固化的历史归属和安全标签
  快照。
- 拼车管理员能够按车辆、用户、账号和自定义 UTC `[from, to)` 查询聚合；乘客
  只能使用固定周期。查询必须说明保留窗口和未知用量数。
- 用量默认保留 90 天，审计默认保留 180 天，均可配置。清理不得破坏仍在保留期
  内的聚合一致性。

### R8：审计、安全与运维

- 登录成功/失败、登出、改密、密码重置、会话和 Key 撤销、用户/车辆状态变化、
  成员变更、账号分配变更和权限拒绝必须产生结构化审计事件。迁移失败必须记录
  不含敏感信息的结构化启动日志；仅当 `audit_events` 表已存在且仍可安全写入时，
  才补充持久化审计，不能为了写审计继续使用未知或损坏的 schema。
- 审计、日志、持久化事实和 API 响应不得记录密码、Cookie、Authorization、
  用户 Key、上游 Token/API Key、原始凭据、提示词、响应正文或原始上游错误体。
- 拼车数据库路径必须显式可配置并支持 Docker 持久化卷；启用拼车模块时路径
  不得指向临时目录。
- SQLite 必须自动初始化并使用版本化前向迁移。迁移失败或发现高于当前程序的
  schema 版本时，拼车模块拒绝启动，不得带未知结构继续服务。
- 第一阶段只支持单机、单 CPA 进程写入数据库，不支持通过网络文件系统共享同一
  SQLite 文件。
- 必须提供一致的停机备份与恢复说明，并验证包含 WAL 中已提交数据。恢复操作在
  服务停止时完成，并校验 schema 版本。
- `/carpool/` 静态应用随二进制发布，不依赖运行时网络下载或 Node 工具链；其
  CSP、缓存、会话和 API 权限边界与 `/management.html` 分离。
- 静态应用路由不得使用会与 `/carpool/api/*` 冲突的 Gin catch-all；未知拼车 API
  必须返回 JSON 404，不能回退为前端 HTML。
- 拼车功能默认关闭。关闭时不创建业务数据库、不注册用户 Key 提供者和拼车路由，
  现有 CPA 行为保持不变。

## 第一阶段不包含

- 用户自助发现车辆、申请、邀请、上车、下车或换车。
- 乘客新增、修改或删除上游 OAuth/API Key 凭据。
- 用户、车辆或账号硬额度、自动限额、计费、支付、退款或收入分配。
- 公开车辆市场、原生移动应用或第三方身份提供商登录。
- Home 用户调度、多 CPA 实例或 PostgreSQL 拼车业务仓库。
- 用户 Key 的 Responses WebSocket、Realtime 或 wsrelay 访问。
- 与 exclusive 第三方前端鉴权插件同时启用拼车代理鉴权。
- 乘客单请求明细、模型级他人画像、提示词或响应内容查询。
- 在线热备份、长期归档、物理删除或完整合规擦除工作流。
- fork 或合并现有管理中心前端。

## 验收标准

- [x] **AC1（R1、R2）**：无管理员数据库只能通过 TTY 一次性创建首个拼车管理员；
  登录、登出、改密、管理员重置密码、会话过期和 CSRF 测试通过，明文凭证未写入
  参数、数据库、日志或响应（创建/重置时的一次性展示除外）。
- [x] **AC2（R1、R2）**：乘客可创建两个命名 API Key 并分别使用；撤销一个 Key
  不影响另一个 Key 或网页登录，改密只撤销会话，禁用用户则两类访问全部失败；
  管理员账号无法创建或使用用户代理 Key，角色也不能修改。
- [x] **AC3（R2）**：管理密钥、拼车 Cookie、用户 Key、旧全局 Key 的权限矩阵
  自动化测试通过；旧全局 Key 的既有 HTTP、流式和 Home 行为无回归，但访问
  `/carpool/api/*` 被拒绝且不进入拼车报表。启用拼车后匿名代理请求被拒绝，
  exclusive 鉴权插件冲突在启动期失败；跨位置提供两个不同凭证时在任何 provider
  认证前拒绝，相同值重复时可安全去重。
- [x] **AC4（R3）**：管理员能创建车辆并设置席位，加入至少两名乘客；超员、同一
  用户并发加入两辆车、降低席位到当前人数以下均稳定返回 `409`，数据库最终只
  存在一个当前成员关系。
- [x] **AC5（R3、R4）**：管理员能给车辆分配多个上游账号；同一 `AuthID` 并发
  分配给两辆车时只有一个成功。用户换车和账号移车后，新请求只使用新车账号，
  历史请求及用量仍归属原车。
- [x] **AC6（R5）**：两辆车配置互斥账号集合，针对每个开放用户 Key 的协议入口，
  首选、重试、故障转移、混合供应商、插件越界返回、模型回退和范围外亲和命中
  均无法选择另一辆车账号；空集合在任何上游连接前失败。
- [x] **AC7（R5）**：Home、Responses WebSocket、Realtime、wsrelay 和未列入
  白名单的路由对用户 Key 返回明确不支持，且不回退到旧全局凭据池；旧全局 Key
  保持现有行为。
- [x] **AC8（R6）**：乘客只看见自己的当前车辆、成员展示名及聚合用量、本车账号
  安全 DTO；含邮箱、路径、Token、完整 `AuthID`、提示词和错误正文的测试夹具
  不会出现在响应、日志或审计中。
- [x] **AC9（R6）**：账号运行时状态能折叠为五种安全状态；超过 5 分钟的观测被
  标记 `stale`/`unknown`，运行时账号消失时不会显示健康，也不会删除历史。
- [x] **AC10（R7）**：Key 认证失败只产生安全审计；Key 已认证后的无成员、禁用

## 风险与已接受限制

- 最大安全风险是某条重试、插件、亲和或协议入口绕过车辆凭据范围。实施必须先
  完成调用图与内存 scope 探针，未证明的入口不开放用户 Key。
- 现有用量 reporter 会用全零记录补齐缺失 usage。实施必须增加明确的
  `usage_known` 并贯通逻辑请求 ID；在探针完成前不把事件数量宣传为请求数。
- SQLite 足以支撑第一阶段单实例，但不解决水平扩展。未来多实例需要独立的
  PostgreSQL 仓库与迁移任务，而不是共享 SQLite 文件。
- 用量持久化仍可能在进程崩溃窗口缺失，第一阶段承诺可观察和不误报，不承诺严格
  一次计费。

## 阻塞问题

无用户所有的阻塞决策。SQLite 驱动、调用图和用量事件的具体接线由实施前技术
探针验证；探针失败时缩小用户 Key 路由白名单或采用等价纯 Go 驱动，不改变上述
产品与安全契约。
