## 缺陷与风险

### P1：上游凭据可经响应正文反射给客户端并写入请求日志

**现象**

`xy_gateway` Mock 的正常 Chat 响应包含用于测试的 `_received_headers` 字段，其中回显了 CLIProxyAPI 添加的上游 `Authorization`。CLIProxyAPI 将该字段原样返回给下游客户端；开启 `request-log` 后，同一上游凭据还以完整明文进入请求日志的响应正文部分。

CLIProxyAPI 对请求 Header 本身做了掩码，但没有防止上游响应正文携带代理管理的凭据。

**影响**

配置型 OpenAI-compatible 或 Claude 上游若错误地回显请求 Header，或者上游被恶意控制，普通下游调用者可以获取管理员配置的上游 API Key；启用请求日志时凭据还会持久化到磁盘。

**证据**

- 下游响应：`evidence/smoke/chat.json` 及热加载探针响应。
- 请求日志：`${TEST_ROOT}/auths/logs/` 中命中虚构上游 Key 的文件。
- 本轮共发现 225 个包含虚构上游 Key 的请求日志文件；数量较大是并发测试重复产生所致。

报告不复制完整虚构 Key，避免让报告本身形成错误示例。

**建议**

明确上游响应的信任边界和脱敏合同。至少应在写请求日志前对响应正文中的已知配置凭据做精确值脱敏；若产品要求任何上游都不能把配置凭据返回客户端，还需在下游响应路径增加精确凭据值替换，并补充二进制、JSON、SSE 场景测试。

### P1：上游返回畸形 JSON 时仍向客户端返回 HTTP 200 和畸形正文

**现象**

OpenAI-compatible Chat 和 Claude 上游返回 `Content-Type: application/json` 但正文为畸形 JSON 时，CLIProxyAPI 对客户端仍返回 200，正文也是原始畸形内容。

**实际结果**

```text
Chat:   HTTP 200 + malformed body
Claude: HTTP 200 + malformed body
```

**影响**

客户端无法依赖 HTTP 状态判断请求成功；日志和用量链路可能将上游协议错误误记为成功；调用方通常会得到 JSON 解码错误而不是可处理的代理错误对象。

**证据**

```text
/tmp/cliproxy-live-20260919T050126Z/evidence/malformed-corrected/
```

**建议**

非流式执行器在转发成功响应前验证目标协议的最小合法结构。畸形 JSON 应转换为 502 类上游协议错误，并保证失败用量与日志状态一致。

### P2：原子替换配置文件后 watcher 未重新绑定，后续热加载失效

**现象**

使用同目录临时文件加 `mv` 原子替换 `config.yaml` 后：

1. watcher 没有应用新配置；
2. 随后直接写入新 inode 也没有产生 reload；
3. 重启 CLIProxyAPI 后，对同一文件进行原地 WRITE 能正常触发 `config successfully reloaded`。

这说明 watcher 可能绑定了旧 inode，文件被替换后没有监控父目录并重新注册目标文件。

**影响**

常见编辑器、部署工具和配置管理系统使用原子替换保存配置。CLIProxyAPI 可能继续使用旧配置，同时磁盘上显示新配置，造成运维误判；后续修改也不会生效，直至重启。

**证据**

```text
/tmp/cliproxy-live-20260919T050126Z/evidence/hot-reload/
```

其中磁盘配置已经指向错误 Mock，但请求仍返回正常 200；重启后的原地写入则正常变为 400。

**建议**

监控配置所在目录并处理 `CREATE`、`RENAME`、`REMOVE`，目标路径 inode 变化后重新建立 watch。新增“临时文件写入 + rename 覆盖 + 再次修改”的回归测试。

### P2：不完整 SSE 的下游失败信号不一致

**现象**

- Responses：上游缺少 `response.completed` 时，下游发出结构化 `event: error`。
- Chat：上游没有 finish reason 和 usage，但代理仍补发 `[DONE]`。
- Anthropic：上游没有 `message_stop`，代理直接结束连接，没有结构化错误事件。

Go 实机驱动器将三者均判定为 `invalid_sse`，但普通客户端可能把 Chat 的 `[DONE]` 当成成功结束，Anthropic 客户端只能从缺少终态推断失败。

**证据**

```text
/tmp/cliproxy-live-20260919T050126Z/evidence/incomplete/
/tmp/cliproxy-live-20260919T050126Z/evidence/driver-incomplete-*.jsonl
```

**建议**

统一流式完整性合同：缺少协议终态时不得生成成功终止标记；在下游已经发送 200 的情况下，尽可能发送该协议允许的错误事件并结束连接，同时把日志/usage 标记为不完整失败。

## 其他观察

- 100 个并发请求没有下游 `X-Request-Id`、`OpenAI-Request-Id` 或 `X-CPA-Trace-Id` 响应 Header；应用日志内部有请求 ID。当前未将其判定为缺陷，因为需要先确认公开 API 合同是否承诺回传。
- Mock 用毫秒时间生成响应 ID，100 并发中出现重复响应 ID。这属于测试夹具特性，不归入 CLIProxyAPI 缺陷。
- xy_gateway global teardown 关闭了测试监听端口，但进程未在等待窗口内退出，最终按记录的进程组执行了强制清理。未修改 xy_gateway，也未将其归入 CLIProxyAPI 缺陷。
