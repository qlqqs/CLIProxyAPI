# 独立审查与收敛协议

本协议用于复杂 Trellis 规划。它定义审查覆盖面、每轮输入输出和停止条件；具体 `trellis channel` 命令以相邻 `trellis-channel` Skill 的当前文档为准。

## 一、准备审查上下文

主代理先完成以下工作：

1. 确认当前任务仍为 `planning`。
2. 从用户消息和任务文档中提取“已冻结决策”，放进审查 brief。reviewer 可以指出决策的风险或矛盾，但不能擅自改写它们。
3. 列出尚待收敛的事项，并区分：
   - 用户必须决定的产品、范围、体验、兼容性或风险取舍；
   - 可以由仓库证据回答的技术事实；
   - 可以采用安全默认值的实现细节；
   - 可以推迟且不改变 MVP 行为的技术未知。
4. 给 reviewer 注入最少但完整的上下文：当前 PRD、已有设计/实施计划、相关 research，以及适用于审查的 JSONL 清单。不要注入整段聊天记录或无关文件。
5. 明确 reviewer 只读，不得编辑工作区、实现代码、启动任务或提交 Git。

审查 brief 至少包含：目的、冻结决策、审查问题、证据要求、输出格式和禁止动作。

## 二、多轮压力测试

审查轮次应围绕不同失败模式展开。可以合并不相关或明显不适用的轮次，但不得因为 reviewer 第一轮表示赞同就结束。

### 轮次 A：方向与 MVP 边界

要求 reviewer 独立回答：

- 当前问题的最小本质是什么；方案是否直接解决它。
- 应复用现有机制、扩展边界还是增加新模块。
- 哪些属于第一阶段，哪些应推迟；什么证据会迫使推迟项回到第一阶段。
- 是否存在更简单方案，以及当前方案增加的每项复杂度由哪条需求驱动。

输出必须包含明确推荐、主要代价、被否决方案和仓库 `file:line` 证据。

### 轮次 B：反方论证

让同一 reviewer 主动攻击上一轮及主方案：

- 找出武断默认、未经用户授权的产品假设和看似合理但无法验收的表述。
- 检查方案是否损害现有兼容性、扩张第一阶段范围或制造长期维护负担。
- 区分真正的安全要求与偏好，不因“更完整”而自动加入功能。
- 对每个反对意见给出最小修正，而不是重写全部方案。

### 轮次 C：领域、数据与权限契约

要求把原则压成可实现契约：

- 实体、关键字段、状态机、唯一约束、外键与删除语义。
- 身份、角色、凭证、授权快照、撤销和并发冲突边界。
- 请求、事件、用量或审计事实的来源、关联键、未知值与重复语义。
- 管理员、普通用户和系统进程的权限矩阵。
- 每个强业务规则是否有数据库或不可绕过的底层约束，而非只靠 UI。

若现有代码无法证明某个数据语义，要求把它改写为实现前技术探针，不得伪装成已确认事实。

### 轮次 D：用户体验与运维闭环

覆盖一个真实操作者从初始化到故障恢复的完整路径：

- 首个管理员或根身份如何安全创建。
- 创建、禁用、恢复、轮换、分配、冲突和撤销如何操作。
- 正常、空状态、无权限、陈旧状态、部分失败和服务不可用时用户看到什么。
- 部署依赖、持久化路径、迁移失败、备份恢复、数据保留、审计与日志如何处理。
- 新界面或 API 如何与现有入口共存，不泄露更高权限凭证。

不要用页面文案替代后端状态和错误契约。

### 轮次 E：跨层可行性与发布阻断

让 reviewer 沿真实调用图检查：

- 每个入口能否把身份与授权约束传到所有选择、重试、故障转移、缓存、异步和长连接路径。
- 快路径、插件、会话亲和、后台任务或兼容入口是否能绕过新约束。
- 观测事件是否真的具备方案依赖的 ID、终态、字段存在性和顺序保证。
- 构建、打包、迁移、回滚及旧行为兼容是否可验证。
- 哪些测试失败必须阻断发布，哪些只是后续优化。

输出应给出调用图锚点、最小技术探针和 fail-closed 条件。

## 三、每轮收敛动作

主代理收到结果后按以下顺序处理：

1. 使用 `messages --raw` 读取完整结果，区分 reviewer 的证据、推断和建议。
2. 对关键 `file:line`、配置、测试行为或命令在当前仓库重新核验。
3. 将发现分类为：
   - `采纳`：回写 PRD、设计或实施计划；
   - `部分采纳`：写清保留与拒绝部分；
   - `拒绝`：记录与用户目标、仓库事实或范围冲突的理由；
   - `技术探针`：实现前必须用代码或测试证明；
   - `用户决策`：按 `trellis-brainstorm` 只问一个最高价值问题。
4. 更新经过整理的 `research/<topic>-review.md`。保留结论、证据和取舍，不复制频道全文。
5. 再发送下一轮时，只说明已变化的契约和本轮要挑战的问题，避免把预期答案写进提示词。

## 四、最终反方审查

最终审查必须读取最新的 `prd.md`、`design.md`、`implement.md`、相关 research 和上下文清单，并至少检查：

- 文档间是否有字段、状态、默认值、范围或术语矛盾。
- 是否仍有未解决的用户所有决策。
- 每条验收标准能否映射到明确实现步骤和验证方法。
- 安全边界是否覆盖所有入口和重试路径，并默认拒绝未证明路径。
- 数据模型、并发、迁移、清理、恢复和历史归属是否自洽。
- 兼容范围、回滚点、日志、审计和敏感信息 DTO 是否完整。
- JSONL 清单是否有效、非空且只包含相关上下文。

要求 reviewer 按严重级别列出具体“文件 + 章节”发现和最小修订建议。不要要求它给出预设结论。若无实质问题，让它明确说明可以提交用户进行最终规划批准。

## 五、复审与停止条件

最终审查不是一次性盖章：

- 接受的实质发现回写后，应复审受影响契约及其相邻边界。
- 如果 worker 已完成并退出，先检查 channel 状态；需要延续上下文时按 `trellis-channel` 规则恢复或重新 spawn，再使用 `requireRunningWorker` 发送。`undeliverable` 不能算作已审查。
- 等待完成信号使用 Trellis 生成的 `done`、`turn_finished` 或 `error` kind，不把普通自定义 tag 当完成信号。
- 超时或输出截断时，先按 `trellis-channel` 的调试流程查看 raw 消息与 worker 状态，不盲目重复启动代理。

满足以下条件即可停止，不为追求形式上的轮次数继续循环：

- 所有影响行为、安全、一致性、可实现性或验收的发现均已处置。
- 剩余意见只是明确标注的编辑建议或不改变 MVP 的后续优化。
- reviewer 明确认为方案可以交给用户最终批准。
- 主代理独立运行规划校验，并确认任务仍为 `planning`。

## 六、本地收尾校验

根据项目实际工具执行等价检查，通常包括：

```bash
python3 ./.trellis/scripts/task.py validate <task>
git diff --check
```

另外人工确认：

- `prd.md` 已完成无损 convergence pass。
- 复杂任务具备 `design.md` 与 `implement.md`。
- 子代理工作流的 `implement.jsonl`、`check.jsonl` 都是有效、非空且引用存在的 JSONL。
- research 中记录了已冻结决策、审查发现处置和剩余风险。
- 没有运行 `task.py start`，没有修改业务代码。

最后向用户汇报目标、范围、关键决策、验收与风险，并请求对这份最新摘要进行单独批准。
